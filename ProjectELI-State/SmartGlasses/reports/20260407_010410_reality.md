# Reality Check for SmartGlasses Project

## Subtitle Placement: Feasible Now

### Current State
- The glasses should display subtitles in a way that is readable, stable, and non-distracting.
- Early tests are being conducted through the `TranscriptLab` app.

### Constraints
- Must remain socially acceptable.
- Needs to be clear enough for real-time conversations.
- Should not become distracting.

### Feasibility Analysis
- **Subtitle Placement:** Placing subtitles directly in the user's line of sight but slightly off-center (e.g., above or below the field of view) can help maintain clarity and non-distractiveness. This aligns with initial tests conducted through `TranscriptLab`.

**Conclusion:**
- **Feasible Now**: The current approach to subtitle placement is feasible within the given constraints.

## Confidence Display: Feasible Later

### Current State
- The confidence display format needs refinement.
- Initial options include labels only, label + short reason, or score + label.

### Constraints
- Needs to build trust without being too complex.
- Must remain readable and non-distracting during real-time interactions.

### Feasibility Analysis
- **Confidence Display Options:**
  - Labels Only: Simple but may lack detail.
  - Label + Short Reason: Provides more context but might be cluttered.
  - Score + Label: Can offer nuanced information while remaining concise.

Given the current focus on core deepening and the need to avoid overloading the user, a simple label-only approach could be feasible for initial testing. However, further refinement will be necessary as we move towards more complex interactions.

**Conclusion:**
- **Feasible Later**: A more detailed confidence display format can be explored once basic functionality is validated.

## Memory/Cache Policy: Feasible Now

### Current State
- Face/name recall should expose uncertainty clearly.
- Early versions should rely heavily on phone processing, with cloud optional where useful.

### Constraints
- Phone-first runtime.
- Heavy local caching to reduce dependency on cloud.

### Feasibility Analysis
- **Memory/Cache Policy:** Implementing a simple cache mechanism on the phone for frequently accessed face and name data is feasible. This can be done through local storage solutions like SQLite or Core Data, which are well-established technologies.

**Conclusion:**
- **Feasible Now**: A basic memory caching policy using local storage can be implemented to support offline functionality while keeping the system lightweight.

## Phone/Cloud Boundary: Feasible Now

### Current State
- The primary runtime for speech, context, and memory lookup should happen on the phone.
- Cloud usage is optional where it adds clear value and latency remains acceptable.

### Constraints
- Phone-first approach with minimal cloud dependency.
- V1 interaction through frame touches only.

### Feasibility Analysis
- **Phone/Cloud Boundary:** Current implementation in `TranscriptLab` aligns well with this constraint. The app uses local processing for speech transcription and display, making it feasible to keep the system phone-centric until further needs arise.

**Conclusion:**
- **Feasible Now**: The current architecture respects the phone-first runtime and minimal cloud dependency, ensuring V1 interaction through frame touches only.

## Visual Hierarchy: Feasible Now

### Current State

### Constraints
