# Reality-Checked Directions

## Subtitle Placement: Feasible Now
### Reason:
The current `TranscriptLab` app provides a basic framework for testing subtitle behavior on the phone side. Since the focus is on real-time clarity and stability, feasible placements can be iterated within this environment. For now, a simple center placement with minimal overlap (to avoid distraction) would be practical and aligns with the core mission of providing usable, unobtrusive assistance.

## Confidence Display: Feasible Now
### Reason:
Given that the `TranscriptLab` app is designed to test confidence behavior, it can serve as an early ground for experimenting with different confidence formats (label only, label + short reason, or score + label). The goal should be to identify a format that balances clarity and trust without overwhelming the wearer.

## Memory/Cache Policy: Feasible Now
### Reason:
The `TranscriptLab` app can help refine memory caching policies by testing how different levels of local storage impact real-time performance and battery consumption. For instance, caching face/name pairs with limited sessions or periodic refreshes could be tested to find a balance between utility and resource management.

## Phone/Cloud Boundary: Feasible Now
### Reason:
The `TranscriptLab` app is designed to test phone-first processing paths, which can inform the boundary between local and cloud computations. Early experiments should focus on scenarios where minimal or no cloud dependency is required, ensuring that the system remains lightweight and reliable.

## Visual Hierarchy: Feasible Now
### Reason:
By using `TranscriptLab` for initial testing, visual hierarchy can be iterated to find a balance between subtitle clarity and non-intrusive design. For example, subtitles could start with simple text placement, gradually incorporating confidence indicators or other UI elements as they are developed.

## V1 Core Deepening: Likely Waste of Time
### Reason:
Given the current focus on core deepening through subtitle quality, memory trust, and visual UX improvements within `TranscriptLab`, broad feature expansion beyond these core areas is likely a waste of time. The project should continue to refine these critical components while surfacing real-world constraints early.

## Constraint Pressure: Feasible Now
### Reason:
The `TranscriptLab` app provides an excellent platform for surface and manage constraints such as battery, latency, privacy, and usability limits. Early iterations can help identify weak areas and prioritize improvements accordingly.

## Interaction Constraints: Feasible Later
### Reason:
While the current interaction focus is on frame touches, exploring broader interaction patterns (e.g., voice commands) in future versions could be useful. For now, it's more critical to ensure that the V1 interaction model remains robust and aligned with user needs.

## Privacy vs Usefulness: Feasible Now
### Reason:
The `TranscriptLab` app can help surface privacy concerns early by testing how much information is required for effective memory support without compromising user trust. Balancing these needs within the current context is crucial.

## Always-On Sensing vs Battery and Thermals: Feasible Later
### Reason:
Given the V1 frame-touch-only interaction model, always-on sensing is not a primary concern yet. As the project evolves to include more complex interactions, this constraint will become more relevant and can be addressed then.

## Rich Context vs Low-Latency Response: Feasible Now
### Reason:
The `TranscriptLab` app can help refine real-time processing paths to ensure that context is provided as quickly and accurately as possible. Early experiments with low-latency responses in the current interaction model are feasible and valuable.

## Discreet UX vs Enough Visual Clarity: Feasible Later
### Reason:
As the project moves beyond V1, more complex visual designs can be tested to balance discreetness with clarity. For now, focusing on a simple yet effective design within `TranscriptLab` is sufficient.
