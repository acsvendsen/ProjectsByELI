## Reality Check Summary

### Subtitle Placement
**Subtitle Placement**: Feasible now.

- **Reasoning**: The glasses should remain lightweight and socially acceptable, which means subtitles need a clear and unobtrusive placement that is readable in motion. Based on the current `TranscriptLab` design, subtitles can be placed at the bottom of the display with minimal overlap from the frame or other UI elements. This ensures they are visible but do not distract too much.

### Confidence Display
**Confidence Display**: Feasible now.

- **Reasoning**: The confidence format should build trust without overwhelming the user. A simple label + short reason (e.g., "90% sure") might be appropriate for V1, as it provides enough transparency while keeping the interface clean. This aligns with the current focus on low-friction assistance and clear feedback.

### Memory/Cache Policy
**Memory Cache Policy**: Feasible now.

- **Reasoning**: For face/name memory caching, the glasses can rely on a phone-first approach where locally cached data is used for quick lookup but still synchronized with cloud storage. This ensures that memory remains up-to-date while reducing battery and thermal pressure.

### Phone/Cloud Boundary
**Phone/Cloud Boundary**: Feasible now.

- **Reasoning**: The current architecture emphasizes phone-first processing, which means heavy computation should be offloaded to the phone or optional cloud services only when clearly justified. For V1, this approach is feasible as it simplifies local hardware requirements and leverages existing phones for processing power.

### Visual Hierarchy
**Visual Hierarchy**: Feasible now.

- **Reasoning**: The visual hierarchy should prioritize clarity over feature density. Subtitles and one-line prompts need to be designed with a clear distinction in mind, ensuring that subtitles remain the primary focus while additional information like confidence labels are secondary but still visible.

### Core Deepening vs. Feature Sprawl
**Core Deepening Over Sprawl**: Feasible now.

- **Reasoning**: The project should continue to focus on improving subtitle quality, memory trust, and visual UX rather than broad feature expansion. This ensures that the core mission remains at the forefront of development efforts.

### Privacy vs. Usefulness
**Privacy vs. Usefulness**: Feasible now.

- **Reasoning**: The system must strike a balance between providing useful assistance without invading user privacy. For V1, this can be achieved by clearly exposing uncertainty and avoiding any form of data collection that could be perceived as invasive.

### Always-On Sensing vs. Battery and Thermals
**Always-On Sensing vs. Battery and Thermals**: Feasible later.

- **Reasoning**: Early versions should remain lightweight and socially acceptable, which means always-on sensing is not feasible now due to thermal and battery constraints. However, this can be explored as the hardware evolves and better power management techniques are implemented.

### Real-time Subtitle Clarity
**Real-time Subtitle Clarity**: Feasible now.

- **Reasoning**: The glasses should provide subtitles that remain readable, stable, and trust-preserving in live conversation. The current `TranscriptLab` setup can be refined to ensure this by optimizing the subtitle rendering pipeline and ensuring it stays within real-time constraints.

### Memory Support for Names and Prior Context
**Memory Support for Names and Prior Context**: Feasible now.

- **Reasoning**: V1 should focus on basic memory support that helps recall names, people, and prior context. This can be implemented through a local cache on the phone with periodic updates from the cloud to maintain accuracy and relevance.

### Low-friction Assistance
**Low-friction Assistance**: Feasible now.

- **Reasoning**: The system should provide one-line help and visible support without creating command overhead or social awkwardness. Frame-touch interactions can be designed to minimize user effort while still providing useful assistance.

### Interaction Constraints
**Frame Touch Only V1**: Feasible now.

- **Reasoning**: Early versions should not depend on voice activation or spoken user commands, as these require more complex hardware and software components that are not feasible with current constraints. Frame-touch interactions align well with the current focus on simplicity and usability.

### Summary of Reality Rules
- The project should continue to focus on core-deepening work that improves subtitle quality, memory trust, and visual UX.
- V1 interaction should remain frame touch-only to avoid adding unnecessary complexity.
- Privacy concerns must be managed by clearly exposing uncertainty and avoiding invasive data collection.
- Real-time constraints require careful optimization but are feasible now with the current setup.

By following these guidelines, the project can continue to make progress while respecting real-world limitations.
