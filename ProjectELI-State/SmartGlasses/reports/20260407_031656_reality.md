## Reality Check for SmartGlasses Core Field

### Feasibility Assessments

#### Subtitle Clarity (subtitle_clarity)
- **Current Status:** Feasible Now  
- **Reasoning:**  
  - The `TranscriptLab` app already validates real-time transcript behavior, ensuring subtitles are clear and stable enough. 
  - Hardware constraints for displaying text on smart glasses are well understood within the project.
  - V1 interaction is frame-touch only, which simplifies subtitle placement and display logic.

#### Memory Trust (memory_trust)
- **Current Status:** Feasible Now  
- **Reasoning:**  
  - The `TranscriptLab` app can simulate memory recall by storing face names and prior context in a simplified model.
  - Confidence objects and reinforcement learning can be implemented to ensure the system does not create corrupted recall.

#### Low-Friction Assistance (low_friction_assistance)
- **Current Status:** Feasible Now  
- **Reasoning:**  
  - V1 interaction is frame-touch only, reducing command overhead and maintaining a low-friction user experience.
  - One-line prompts can be designed to appear as needed without overwhelming the wearer.

### Additional Real-world Constraints

#### Frame-Touch-Only V1 Interaction
- **Current Status:** Feasible Now  
- **Reasoning:**  
  - The current implementation respects frame-touch interactions, which is a hard constraint for V1. This ensures the product remains discreet and user-friendly.

#### Phone-First Runtime
- **Current Status:** Feasible Now  
- **Reasoning:**  
  - Early versions rely heavily on phone processing, reducing battery pressure and thermal issues.
  - The `TranscriptLab` app provides a practical test bed for early interactions without heavy glasses hardware.

### Open Questions

1. **Subtitle Placement:**
   - **Current Status:** Assumptions Needing Evidence
   - **Reasoning:**  
     - The current implementation does not explicitly define subtitle placement, which could impact readability and social acceptability.
     - Concrete candidate options should be explored to ensure subtitles are visible yet unobtrusive.

2. **Confidence Display:**
   - **Current Status:** Assumptions Needing Evidence
   - **Reasoning:**  
     - The confidence display format is not explicitly defined, which could affect trust and user perception.
     - Options like a label only, label + short reason, or score + label should be evaluated for V1.

3. **Memory/Cache Policy:**
   - **Current Status:** Assumptions Needing Evidence
   - **Reasoning:**  
     - The cache policy on the phone is not explicitly defined.
     - Decisions should be made based on balance between memory usage and recall speed, considering privacy constraints.

4. **Phone/Cloud Boundary:**
   - **Current Status:** Feasible Now (with caveats)
   - **Reasoning:**  
     - The initial design favors phone-first processing but allows for cloud support where clearly justified.
     - As the project evolves, this boundary may shift based on real-world needs and constraints.

5. **Visual Hierarchy:**
   - **Current Status:** Assumptions Needing Evidence
   - **Reasoning:**  
     - The visual hierarchy of subtitles and one-line prompts is not explicitly defined.
     - Concrete candidates should be explored to ensure a clear and unobtrusive user interface.

### Summary

- **Subtitle Clarity, Memory Trust, Low-Friction Assistance:** Feasible Now. These core features can be implemented with the current project setup and constraints.
- **Subtitle Placement, Confidence Display, Memory/Cache Policy, Visual Hierarchy:** Assumptions Needing Evidence. Concrete decisions are required to ensure these areas meet user needs without compromising real-world constraints.

By focusing on concrete candidate options for these open questions, the project can continue to deepen its core mission while ensuring high usability and trustworthiness.
