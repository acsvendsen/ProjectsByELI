### Idea 1: Subtitle Placement

1. **Why it benefits the core**

   By defining a consistent subtitle placement rule based on confidence level, the system can ensure that subtitles remain visible and useful without overwhelming the wearer. This improves the core attractor of real-time subtitle clarity by maintaining readability across different conversation contexts.

2. **What small change unlocks it**

   Introduce two subtitle placement rules: one for high-confidence matches (e.g., names and faces) where subtitles are placed prominently but briefly, and another for lower-confidence matches (e.g., background conversations or less critical context) where subtitles appear in a more subtle position to avoid distraction.

3. **Likely payoff**

   This change will enhance the wearer's trust in the system by ensuring that key information is always clear while reducing visual clutter in less critical situations. It aligns with the core attractors of real-time subtitle clarity and low-friction assistance, making interactions smoother and more focused.

4. **Immediate next probe**
   - Define one fixed subtitle position rule for V1: keep subtitles at the bottom center of the display.

   By implementing a clear and concise confidence display format, the system can better manage wearer trust. When subtitles or memory support are shown with high-confidence indicators, it increases the likelihood that the wearer will find the assistant reliable, which in turn enhances their overall experience and satisfaction.

4. **Immediate next probe**

### Idea 3: Memory/Cache Policy

1. **Why it benefits the core**

   By setting a local cache size threshold for face/name memory, we ensure that the system can reliably recall names and faces with minimal lag while keeping resource usage low. This helps in maintaining a balance between rich memory support and efficient processing, which is crucial for real-world usability and trust.

2. **What small change unlocks it**

   Define a local cache size limit of 10-15 recent entities (faces/names) that the system remembers on the phone before evicting older entries to make room for new ones.

3. **Likely payoff**

   This approach ensures that the system can quickly recall names and faces within recent interactions, reducing latency and enhancing the wearer's trust in the memory support. It also helps in managing resources effectively without sacrificing too much memory capacity.

4. **Immediate next probe**
   - Set one local cache eviction rule for face/name memory in V1.

### Idea 4: Phone/Cloud Boundary

1. **Why it benefits the core**

   Staying with the phone-first runtime ensures that early versions of the glasses remain lightweight and socially acceptable. By carefully defining what stays on the phone versus what falls back to the cloud, we can minimize battery drain while still delivering useful functionality.

2. **What small change unlocks it**

   Define a clear local cache eviction policy for face/name memory, ensuring that only recently seen or frequently encountered names are cached locally to avoid overwhelming the phone's storage and processing capabilities.

3. **Likely payoff**

   By limiting the amount of memory data stored on the phone, we can reduce battery usage and ensure that the glasses remain responsive in live conversations. This will enhance user trust by maintaining a balance between utility and resource efficiency.

4. **Immediate next probe**
   - Choose one phone-local versus cloud fallback boundary for face/name recall lookup in V1.
