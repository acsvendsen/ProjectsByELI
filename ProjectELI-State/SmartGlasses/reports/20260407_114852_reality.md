# Reality Check for SmartGlasses Core Field

## Subtitle Clarity (Subtitle Placement)
- **Feasible Now**: 
  - **Current State**: The project is focused on clear, stable subtitles that can be trusted in live conversation.
  - **Constraints**: Early glasses should remain lightweight and socially acceptable; glasses hardware should remain simple to avoid thermal and battery pressure.
  - **Reasoning**: Given the current implementation of `TranscriptLab`, we have a good understanding of real-time subtitle clarity. The project has not yet explored complex placements that might be distracting, so subtitles can be placed at the top or bottom corners for now.

## Memory Trust (Memory/Cache Policy)
- **Feasible Now**:
  - **Current State**: The system should remember names and faces without overconfidence.
  - **Constraints**: Early hardware remains simple, with heavy processing on the phone. Confidence in memory recall must be clear and not misleading.
  - **Reasoning**: Using a combination of local caching on the phone for recent interactions (e.g., face/name pairs) while still allowing cloud-based reinforcement can ensure both speed and trust. A confidence object could display as "possibly known" or "recently seen," which would help maintain user trust.

## Low Friction Assistance (Visual Hierarchy)
- **Feasible Now**:
  - **Current State**: One-line prompts should coexist with subtitles without overwhelming the wearer.
  - **Constraints**: Interaction should happen through frame touches, and visual clarity must remain socially acceptable.
  - **Reasoning**: Subtitles can be displayed prominently at the top or bottom of the field of vision. One-line prompts could appear as brief, temporary text overlays that do not obscure primary content but are still easily readable.

## Phone/Cloud Boundary
- **Feasible Now**:
  - **Current State**: The phone should handle heavy processing while cloud support is optional.
  - **Constraints**: Heavy on-glasses computation risks battery and thermal issues; early versions should focus on minimal local logic.
  - **Reasoning**: For V1, the system can rely heavily on the phone for speech processing, context lookup, and memory management. Cloud support can be added later if it significantly improves performance without compromising usability.

## Confidence Display
- **Feasible Now**:
  - **Current State**: Confidence should be represented in a way that maintains user trust.
  - **Constraints**: Simplified confidence display is preferred to avoid social awkwardness or overconfidence.
  - **Reasoning**: A simple confidence label (e.g., "possibly known," "recently seen") can be used to indicate the reliability of memory recall. This approach ensures transparency and helps maintain user trust.

## Interaction Constraints
- **Feasible Now**:
  - **Current State**: Interaction should happen through frame touches only.
  - **Constraints**: Early hardware remains simple; heavy on-glasses computation risks battery and thermal issues.
  - **Reasoning**: Frame touch interactions are straightforward to implement and test, reducing the risk of overheating or battery drain. This approach aligns with current implementation constraints.

## Battery and Thermal Pressure
- **Constraint Pressure**:
  - **Current State**: Heavy local processing is risky; early versions should rely on phone-first processing.
  - **Constraints**: Glasses hardware must remain socially acceptable and lightweight to avoid thermal and battery issues.
  - **Reasoning**: Given the current state of `TranscriptLab` and the focus on minimal local logic, this approach is feasible. Ensuring that heavy processing happens on the phone reduces the risk of overheating or excessive power consumption.

## Privacy vs Usefulness
- **Constraint Pressure**:
  - **Current State**: The system should not pretend certainty in memory recall.
  - **Constraints**: Early hardware remains simple; heavy local computation risks battery and thermal issues.
  - **Reasoning**: By using confidence objects to indicate the reliability of memory recall, the system can maintain privacy while still providing useful assistance.

## Fast Lookup vs Low Latency Response
- **Constraint Pressure**:
  - **Current State**: The system should provide timely help without overloading the runtime.
  - **Constraints**: Early hardware remains simple; heavy local computation risks battery and thermal issues.
  - **Reasoning**: A combination of local caching on the phone for recent interactions with cloud-based reinforcement can ensure fast lookup while maintaining low latency.

## Discreet UX vs Visual Clarity
- **Constraint Pressure**:
  - **Current State**: Display behavior should remain socially acceptable while still being readable in motion and noise.
  - **Constraints**: Early hardware remains simple; heavy local computation risks battery and thermal issues.
  - **Reasoning**: Subtitles can be placed at the top or bottom corners to avoid distracting the wearer. One-line prompts could appear as temporary text overlays that do not obscure primary content.

## Summary
- The project is feasible with the current constraints in place, focusing on core deepening improvements such as subtitle clarity, memory trust, and low-friction assistance.
- Further exploration of subtitle placement, confidence display, and phone/cloud boundary will help refine these areas without introducing unnecessary complexity or risk.
- Ensuring that interactions happen through frame touches only aligns with early hardware constraints and helps maintain social acceptability.
