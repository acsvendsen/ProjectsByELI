# Reality Rules for SmartGlasses Core Field

## Current Direction Feasibility Analysis

### 1. Real-time Subtitle Assistance
- **Feasible Now**: 
  - The glasses can display subtitles in real-time with minimal latency, leveraging modern display and communication technologies.
  - Given the frame-touch interaction model, this feature is straightforward to implement without heavy on-glasses processing.

- **Assumptions Needing Evidence**:
  - Ensure subtitle latency is low enough (e.g., <100ms) for comfortable reading in noisy environments. 
  - Verify that the text can be displayed clearly and discreetly over the wearer's field of vision.

### 2. Face/Name Memory
- **Feasible Now**: 
  - The glasses can automatically remember new faces and names based on context, with reinforcement rules to enhance trust.
  - Touch-based interactions for explicit memory capture are straightforward.

- **Assumptions Needing Evidence**:
  - Demonstrate that entity-linking reliability is high enough to avoid frequent errors in recognizing and storing names.
  - Ensure the memory policy respects user privacy by providing clear opt-out options.

### 3. Confidence Display
- **Feasible Now**: 
  - Confidence can be represented using a label or numeric score, with a short reason for the confidence level displayed next to relevant information (e.g., names).
  - This enhances trust and clarity without overwhelming the user.

- **Assumptions Needing Evidence**:
  - Validate that the confidence system accurately reflects the reliability of recognized entities.
  - Ensure that the display is unobtrusive yet informative enough to be useful.

### 4. One-line Contextual Prompts
- **Feasible Now**: 
  - Short, contextual prompts can provide helpful information without overwhelming the user.
  - These can appear discreetly in the corner of the field of vision or as small pop-ups.

- **Assumptions Needing Evidence**:
  - Ensure that the one-line prompts are relevant and useful to the current context.
  - Test that they do not distract from the primary task (e.g., conversation).

### 5. Visual Hierarchy
- **Feasible Now**: 
  - Subtitles should be positioned above or below speech bubbles, with clear visual hierarchy.
  - The interface design should prioritize ease of reading and minimal distraction.

- **Assumptions Needing Evidence**:
  - Conduct user testing to ensure that the chosen visual hierarchy is intuitive and does not cause discomfort or strain.

### 6. Interaction Model (Frame-Touch Only)
- **Feasible Now**: 
  - Frame-touch interactions are simple and low-friction, aligning well with the V1 design.
  - This interaction model can be extended in future iterations but should remain primary for simplicity.

- **Assumptions Needing Evidence**:
  - Ensure that frame-touch interactions do not conflict with other necessary functions (e.g., adjusting settings).

### 7. Battery and Thermal Constraints
- **Feasible Now**: 
  - The glasses can operate on a standard battery without significant thermal issues, given the low processing requirements.
  - Optimizing for minimal power draw is essential but feasible.

- **Assumptions Needing Evidence**:
  - Monitor battery usage during testing to ensure it remains within acceptable limits.

### 8. Privacy and User Trust
- **Feasible Now**: 
  - Memory policies should be transparent, allowing users to understand how their data is used.
  - Ensuring that memory objects are reliable and accurate will enhance user trust over time.

- **Assumptions Needing Evidence**:
  - Conduct privacy impact assessments to ensure compliance with relevant regulations and user expectations.

### 9. Phone/Cloud Architecture
- **Feasible Now**: 
  - The phone-first architecture is practical given the current hardware constraints.
  - This approach ensures that heavy processing can be offloaded, conserving battery life on the glasses.

- **Assumptions Needing Evidence**:
  - Validate that cloud services are reliable and available when needed.
  - Ensure network latency does not significantly impact real-time performance.

### 10. Drift Risks
- **Core Risk**: Feature sprawl before core subtitle/memory loop is excellent.
  - Focus on refining the core features to ensure they provide maximum value without adding unnecessary complexity.

- **Evolution Rule**: The project should evolve if it strengthens the core mission or improves real-world usefulness.
  - Keep the focus on deepening the core capabilities rather than broad expansion.

## Summary
The current V1 direction appears feasible given the constraints and assumptions. However, early testing and validation are crucial to ensure that the features meet user needs without causing discomfort or overloading the system. Key areas for further evidence include confidence systems, memory policies, and battery usage.
