# Reality Check for SmartGlasses Core Field

## Summary of Current Mission and Constraints
- **Mission**: Create smart glasses as a discreet, context-aware personal assistant focused on live subtitles, face/name recall, conversation memory, and one-line support.
- **Non-negotiables**:
  - No pretense; assist based on actual data.
  - Simple hardware in early stages (display text, record audio/visual).
  - Context must persist across sessions.
  - New faces/names should be remembered with confidence over time.

## Core Attractors
- Real-time subtitle assistance.
- Personal memory support for names and prior conversations.
- One-line contextual prompts rather than overwhelming paragraphs.
- Low-friction UX; assistive, not deceptive.

## Core Tensions
- Privacy vs. usefulness.
- Always-on sensing vs. battery/thermal limits.
- Local processing vs. cloud intelligence.
- Rich memory vs. fast lookup.
- Discreet UX vs. enough visual clarity.

## Drift Risks
- Gimmick over utility.
- Feature sprawl before core is solid.
- High-latency responses breaking trust.
- Storing low-value info instead of relevant data.

## Why It Matters
Reduce social and cognitive friction, especially in noisy environments, hearing-challenged situations, memory-challenged scenarios, and dense multi-person contexts. Stay present, informed, confident without pretending understanding.

## Evolution Rule
Evolve if it strengthens core mission, improves real-world usefulness, or increases trust/clarity/assistive value.

## Current Open Questions
- Best V1 split between glasses, phone, and cloud.
- Face/name memory storage and reinforcement for fast lookup and trust.
- Confidence representation: numeric score, label, short reason.
- Coexistence of subtitles and one-line prompts.
- Which V1 features produce highest daily-use value with lowest complexity.

## Reality Check

### Likely Waste of Time
- **Feature sprawl**: Adding too many features before the core loop is solid. Prioritize subtitle assistance, face/name recognition, and basic conversation memory.
  - *Evidence Needed*: Prove through user feedback that the core functions are valuable without adding extra features first.
  
### Feasible Now
- **Subtitles in noisy environments**: Early prototypes focusing on real-time text display for speech-to-text processing can be tested with simple hardware.
- **Basic face recognition and name recall**: Implement a simple system to recognize faces and store names for the current session. Use cloud services for heavy processing.
  - *Assumptions Needing Evidence*: Face recognition accuracy in low-light conditions, user acceptance of face/name storage.

### Feasible Later
- **Always-on sensing with hardware constraints**: Develop more advanced sensors and improve battery management as technology advances.
- **Cloud-based intelligence**: Integrate more complex AI models for better context understanding and memory recall once hardware capabilities allow it.
  - *Assumptions Needing Evidence*: Battery life improvements, advancements in miniaturized computing.

### Feasible Now with Potential Risks
- **Discreet UX vs. visual clarity**: Optimize display settings to be unobtrusive but still legible for the wearer. 
  - *Risk*: Low visibility could reduce effectiveness; high visibility could compromise discretion.
  
### Assumptions Needing Evidence
- **Battery and thermal limits**: Determine the maximum duration of continuous operation while maintaining acceptable battery life and heat management.
- **Latency constraints**: Establish acceptable response times to ensure real-time usability without breaking user trust.
  - *Evidence Needed*: Test with prototypes in various environments (noisy, quiet) to understand latency requirements.

## Conclusion
- Focus on core functions first: subtitles, face/name recognition, basic conversation memory.
- Prioritize discreet and usable UX while minimizing battery drain.
- Continuously monitor real-world constraints like battery life, thermal management, and user acceptance.

Early development should focus on minimal viable product (MVP) to test core functionality before expanding features. Early iterations should be simple yet effective to ensure the system is both useful and acceptable to users.
