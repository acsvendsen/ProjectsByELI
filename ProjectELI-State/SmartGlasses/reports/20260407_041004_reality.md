# Reality Check Cycle

## Subtitle Clarity (Subtitle Placement)

### Feasibility Analysis
- **Current State**: The `TranscriptLab` test app is used to validate subtitle clarity in real-time environments.
- **Constraints**:
  - Real-time behavior must remain stable and readable.
  - Must not become distracting.

### Feasible Now: 
- **Placement**: Place subtitles just below the line of sight, ensuring they are readable but do not obstruct peripheral vision. The `TranscriptLab` app can be used to test various placement options during live tests.
  
  - **Reasoning**:
    - The glasses should remain socially acceptable and unobtrusive.
    - Subtitles need to be legible even in fast-paced conversations.

### Feasible Later: 
- **Enhancements**: Implement dynamic subtitle positioning based on head movement or gaze direction. This can be tested once the hardware prototype is available, ensuring that subtitles follow the wearer’s gaze for better readability and less distraction.
  
  - **Reasoning**:
    - This feature will add complexity but could significantly enhance user experience in challenging environments.

### Likely Waste of Time: 
- **Fixed Placement**: Setting a fixed subtitle placement without initial testing through `TranscriptLab`.
  
  - **Reasoning**:
    - Without validation from real-world tests, fixing the position might result in an unsatisfactory UX that is not optimized for clarity and readability.

## Confidence Display

### Feasibility Analysis
- **Current State**: The confidence display format needs to be chosen based on user trust.
- **Constraints**:
  - Must expose uncertainty clearly.
  - Should remain unobtrusive.

### Feasible Now: 
- **Display Format**: Use a simple, label-only confidence format that does not provide scores or detailed reasons. This can be implemented in the `TranscriptLab` app and iteratively refined based on user feedback.
  
  - **Reasoning**:
    - Simplicity ensures low friction and avoids overwhelming the user with too much information.

### Feasible Later: 
- **Enhancements**: Implement a more detailed confidence display format (e.g., label + short reason) once initial trust is established. This can be tested in future iterations.
  
  - **Reasoning**:
    - More complex formats can be introduced later when the core functionality is well-established.

### Likely Waste of Time: 
- **Overly Complex Display**: Implementing a detailed confidence display format right from the start without first establishing user trust and validating through `TranscriptLab`.
  
  - **Reasoning**:
    - An overly complex display might confuse users or reduce usability before trust has been built.

## Memory/Cache Policy

### Feasibility Analysis
- **Current State**: Face/name memory should be cached locally on the phone to ensure fast lookup and reliability.
- **Constraints**:
  - Must expose uncertainty clearly.
  - Should maintain privacy while providing useful support.

### Feasible Now: 
- **Policy Implementation**: Implement a local cache for remembered faces and names. Use the `TranscriptLab` app to test memory recall speed and accuracy in various scenarios.
  
  - **Reasoning**:
    - Local caching ensures quick response times without heavy cloud reliance, which is crucial for V1.

### Feasible Later: 
- **Enhancements**: Introduce periodic cloud synchronization to update local caches with new information. This can be done once the basic memory system is robust and trust in its operation has been established.
  
  - **Reasoning**:
    - Cloud sync will provide a more comprehensive database but should not replace the need for local caching.

### Likely Waste of Time: 
- **Overly Complex Cache Management**: Implement complex cache management strategies without first validating basic memory functionality through `TranscriptLab`.
  
  - **Reasoning**:
    - Overcomplicating initial cache policies might lead to unnecessary complexity and decreased user trust.

## Phone/Cloud Boundary

### Feasibility Analysis
- **Current State**: Early versions should rely heavily on phone processing, with cloud optional where clearly justified.
- **Constraints**:
  - Must respect battery and thermal limits.
  - Should ensure low latency for real-time responses.

### Feasible Now: 
- **Boundary Definition**: Define clear boundaries between local and cloud processing. The `TranscriptLab` app can be used to test various interaction paths and ensure that critical processes remain on the phone.
  
  - **Reasoning**:
    - Keeping heavy processing on the phone reduces battery drain and latency, which are key constraints.

### Feasible Later: 
- **Enhancements**: Introduce cloud support for deeper analysis or background processing once the core functionality is well-established. This can be done through iterative testing with the `TranscriptLab` app.
  
  - **Reasoning**:
    - Cloud support should enhance rather than detract from the primary V1 focus on real-time, reliable assistance.

### Likely Waste of Time: 
- **Premature Cloud Reliance**: Assuming cloud processing is necessary for all interactions before validating core functionality through `TranscriptLab`.
  
  - **Reasoning**:
    - Premature reliance on cloud might lead to unnecessary complexity and reduced user trust in the product.

## Visual Hierarchy

### Feasibility Analysis
- **Current State**: The subtitle and one-line prompts should coexist without overloading the wearer.
- **Constraints**:
  - Must remain socially acceptable while being readable.
  - Should not create visual clutter.

### Feasible Now: 
- **Hierarchy Design**: Implement a simple, non-intrusive hierarchy where subtitles are primary and one-line prompts are secondary. Test this through `TranscriptLab` to ensure it does not interfere with the main subtitle experience.
  
  - **Reasoning**:
    - A clear visual hierarchy ensures that critical information is prioritized.

### Feasible Later: 
- **Enhancements**: Introduce more sophisticated visual hierarchy rules once the basic interaction model is validated. This can be done through iterative refinement in future development cycles.
  
  - **Reasoning**:
    - More complex hierarchies can add value but should not detract from initial usability.

### Likely Waste of Time: 
- **Overly Complex Hierarchy**: Designing a highly complex visual hierarchy before validating the core subtitle and prompt interaction model through `TranscriptLab`.
  
  - **Reasoning**:
    - Over-complicating early designs might result in unnecessary complexity that reduces user trust.

## Summary

By focusing on these specific areas, we can ensure that the SmartGlasses project remains grounded in real-world constraints while continuously improving core functionality. The `TranscriptLab` app will be a key tool for validating and refining these features before moving to more complex implementations.
