# Reality Check for SmartGlasses V1 Direction

## Subtitle Placement and Confidence Display (Subtitle Feasibility)

### Current Core Inputs
- The glasses should provide near-real-time subtitles that do not distract but are clearly visible.
- Confidence in the displayed information must be conveyed effectively.

### Real-world Limits
- **Battery Draw**: Any complex rendering, even if subtle, can significantly impact battery life. Subtitle placement and confidence display need to be optimized for minimal energy usage.
- **Latency**: Subtitles should appear as close to real-time as possible to maintain trust.
- **Thermal Pressure**: The display system must remain cool enough not to interfere with the glasses' overall temperature profile.

### Proposed Directions
- **Feasible Now:**
  - **Simple Text Placement**: Place subtitles slightly below and to one side of the wearer’s gaze. This placement minimizes visual clutter while ensuring readability.
  - **Basic Confidence Indicators**: Use a single symbol (e.g., a checkmark or an exclamation mark) next to the subtitle text. Avoid complex animations that could drain battery.

- **Feasible Later:**
  - **Dynamic Placement Algorithms**: Implement algorithms to adjust subtitle placement based on head movements and gaze direction, but defer this until hardware advancements support it.
  - **Advanced Confidence Indicators**: Develop more sophisticated confidence indicators (e.g., a short reason or numeric score) after initial deployments have been tested for battery impact.

### Assumptions Needing Evidence
- The chosen basic symbols for confidence do not significantly affect battery life. 
- Users find the simple placement effective and non-distracting.

## Face/Name Memory (Memory Feasibility)

### Current Core Inputs
- The glasses should remember faces and names with high accuracy but expose uncertainty when needed.
- Memory must persist across sessions to build trust over time.

### Real-world Limits
- **Privacy Perception**: Users must feel that their data is handled responsibly, especially for memory-related features.
- **Battery Draw**: Storing and retrieving memory data can consume significant battery life if not optimized.
- **Cloud Dependency**: Relying too heavily on cloud storage could compromise privacy and introduce latency.

### Proposed Directions
- **Feasible Now:**
  - Use local caching of recent faces and names. Only store minimal identifiers (like hashes or tokenized IDs) to minimize data retention.
  - Implement a confidence system where the glasses can indicate when it is uncertain about someone's identity, prompting the wearer to confirm.

- **Feasible Later:**
  - Integrate cloud storage for more comprehensive memory management and learning. Ensure this is optional and only used with explicit user consent.
  - Develop algorithms to reinforce memory by showing contextually relevant information over time without overwhelming the user.

### Assumptions Needing Evidence
- Local caching of minimal identifiers does not significantly impact battery life or data privacy concerns.
- Users find it acceptable for the glasses to occasionally indicate uncertainty when recognizing someone.

## One-Line Support and Contextual Prompts (Core Functionality)

### Current Core Inputs
- Provide one-line prompts to aid conversation without overwhelming the user.
- These should be contextually relevant and assistive, not intrusive.

### Real-world Limits
- **Battery Draw**: Running any form of real-time text generation and display can drain battery quickly if not optimized.
- **Thermal Pressure**: Ensure that any processing required for generating these prompts does not heat up the glasses.

### Proposed Directions
- **Feasible Now:**
  - Limit one-line support to brief, contextually relevant snippets. For example, providing a quick reminder of someone's name or topic of conversation.
  - Use local processing only, relying on the phone for initial setup and periodic updates.

- **Feasible Later:**
  - Integrate more advanced natural language generation (NLG) capabilities that can provide richer, contextually relevant prompts. This would require significant optimization to ensure minimal battery impact.

### Assumptions Needing Evidence
- Local processing of one-line support snippets does not significantly affect battery life.
- Users find the brief, contextual reminders helpful and non-intrusive.

## Interaction Through Frame Touches (User Experience)

### Current Core Inputs
- V1 interaction is limited to frame touches only. No voice commands or spoken controls are assumed in this version.

### Real-world Limits
- **Thermal Pressure**: Any additional hardware for touch detection can increase thermal load.
- **Battery Draw**: Touch interactions require power, even if minimal.

### Proposed Directions
- **Feasible Now:**
  - Ensure that the touch interaction is as simple and intuitive as possible. Users should be able to adjust settings or request help with minimal effort using frame touches.
  - Optimize for low battery consumption by minimizing unnecessary processing during touch interactions.

- **Assumptions Needing Evidence**
- The design of touch interactions does not significantly impact battery life or user experience in a negative way.

## Summary

### Feasible Now
- Simple subtitle placement and basic confidence indicators.
- Limited local caching of face/name memory with minimal identifiers.
- Brief, contextually relevant one-line prompts using local processing.
- Frame-touch interaction for simple adjustments and requests.

### Feasible Later
- Dynamic subtitle placement algorithms and advanced confidence indicators.
- Optional cloud storage for comprehensive memory management.
- Integration of more sophisticated natural language generation capabilities for one-line support.

### Likely Waste of Time
- Premature optimization of touch interactions or complex UI elements that do not add significant value in V1.

### Assumptions Needing Evidence
- Battery impact and user experience considerations must be validated through testing before proceeding with more advanced features.
