# Reality Check for SmartGlasses V1 Direction

## Subtitle Clarity: Feasible Now

### Current State
- **Subtitle Placement:** More Prominent selected.
- **Confidence Display:** Label + Reason selected.

### Real-world Constraints
- **Battery Draw:** The subtitle display should be optimized to draw minimal power. This can be achieved by using efficient text rendering and ensuring that the subtitles are only displayed when necessary (e.g., in noisy environments).
- **Latency:** Subtitles need to appear near-real-time to maintain user trust, but they do not require complex processing.
- **Visual Clarity:** The subtitle placement should ensure that they are readable without distracting from the primary conversation.

### Feasibility
- **Subtitle Placement:** More Prominent is a good choice as it ensures subtitles are visible in noisy environments where they are needed most. This aligns with user trust and understanding.
- **Confidence Display:** Label + Reason provides clear feedback to the wearer, enhancing their trust in the system's accuracy.

### Conclusion
**Feasible Now**: Given the current hardware capabilities and the need for minimal battery draw, optimizing subtitle placement and confidence display as selected can be implemented effectively without violating real-world constraints.

## Memory Trust: Feasible Later

### Current State
- **Memory Policy:** Recency First selected.
- **Face/Name Memory:** New faces and names should be remembered automatically by default when supported by context, with explicit remember-touch behavior for reinforcement or prioritized capture.

### Real-world Constraints
- **Battery Draw:** Memory operations are resource-intensive. Early versions should rely heavily on the phone for memory storage and processing.
- **Latency:** Fast lookups are crucial but can introduce latency that might affect user trust if not handled properly.
- **Privacy Perception:** The system must respect privacy by avoiding unnecessary data retention.

### Feasibility
- **Memory Policy:** Recency First is a practical approach as it prioritizes recent interactions, reducing the burden on memory storage. However, more complex memory policies (e.g., semantic understanding of contexts) might be too resource-intensive for V1.
- **Face/Name Memory:** While automatic remembering can provide useful context, explicit remember-touch behavior ensures that users are aware and in control of data collection.

### Conclusion
**Feasible Later**: Implementing a simple recency-first memory policy is feasible now. However, more advanced face/name memory policies involving complex entity linking or semantic understanding should be deferred until later versions when hardware capabilities allow for it without significant battery draw.

## Low-friction Assistance: Feasible Now

### Current State
- **One-line Prompts:** Subtitles and one-line prompts coexist to avoid overloading the wearer.
- **Visual Hierarchy:** Subtitles dominate the display, ensuring they remain a high-priority visual element.

### Real-world Constraints
- **Battery Draw:** The glasses should minimize energy consumption. Overly complex interactions or visual elements can drain battery faster.
- **Latency:** Quick response times are necessary to maintain user trust and ensure that assistance is timely.
- **Social Acceptability:** The system must be designed in a way that respects social norms, avoiding commands that might feel intrusive.

### Feasibility
- **One-line Prompts Coexistence:** Displaying subtitles alongside one-line prompts can be managed without overwhelming the wearer. This approach strikes a balance between providing necessary assistance and maintaining readability.
- **Visual Hierarchy:** Dominance of subtitles ensures they are prioritized, reducing the risk of user distraction.

### Conclusion
**Feasible Now**: Given the need for minimal battery draw and quick response times, coexisting subtitles and one-line prompts with clear visual hierarchy is a feasible implementation that aligns well with current hardware constraints.

## Phone/Cloud Boundary: Feasible Later

### Current State
- **Phone First:** Early versions rely heavily on phone processing.
- **Cloud Optional:** Cloud usage should be limited to scenarios where it clearly adds value and does not significantly impact latency or battery draw.

### Real-world Constraints
- **Battery Draw:** Heavy cloud dependency can drain the phone’s battery, affecting the overall user experience.
- **Latency:** Cloud interactions introduce latency that might break real-time assistance.
- **Privacy Perception:** Users may be wary of data being sent to remote servers.

### Feasibility
- **Phone First:** Early versions should focus on local processing with minimal cloud dependency. This approach ensures low-latency and reduced battery draw.
- **Cloud Optional:** As hardware capabilities improve, the system can incorporate more advanced features that leverage cloud resources without compromising user experience or privacy.

### Conclusion
**Feasible Later**: While early versions can benefit from a phone-first architecture, incorporating more advanced cloud functionalities will be feasible later when improvements in hardware and software allow for better handling of latency and battery draw.

## Interaction Constraints: Feasible Now

### Current State
- **Frame Touch Only:** V1 interaction should happen through frame touches.
- **No Voice Activation:** Early versions do not assume voice commands.

### Real-world Constraints
- **Battery Draw:** Voice recognition requires additional processing, increasing battery consumption.
- **Latency:** Voice commands can introduce latency that might affect real-time assistance.
- **Social Acceptability:** Users may find voice commands intrusive or socially awkward in certain contexts.

### Feasibility
- **Frame Touch Only:** Frame touch interaction is a low-friction and battery-efficient approach that aligns well with current hardware constraints.
- **No Voice Activation:** Early versions should focus on minimizing complexity to ensure robust performance without introducing unnecessary features.

### Conclusion
**Feasible Now**: Given the need for minimal battery draw and quick response times, frame touch-only interaction is a feasible implementation that aligns well with current hardware constraints.
