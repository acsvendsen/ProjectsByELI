# SmartGlasses Core Field

## Mission
Create smart glasses that act as a discreet, context-aware personal assistant focused on live subtitles, face/name recall, conversation memory, and one-line support to help the wearer understand and respond better in real-world interactions.

## Non-negotiables
- The glasses help the wearer; they do not pretend knowledge the wearer does not have.
- Early hardware remains simple: display text, record audio/visual input; phone/cloud handles heavy processing.
- V1 interaction is frame-touch only; do not assume voice activation or spoken command control.
- Context must persist across sessions.
- New faces and names should be remembered with confidence objects and reinforcement over time.
- Real-world constraints must be surfaced early: latency, battery, privacy, social acceptability, on-device limits.

## Core Attractors
- Real-time subtitle assistance in noisy environments
- Personal memory support for names and prior conversations
- One-line contextual prompts rather than overwhelming paragraphs
- Low-friction human experience; assistive, not deceptive

## Core Tensions
- Privacy vs usefulness
- Always-on sensing vs battery and thermals
- Local processing vs cloud intelligence
- Rich memory vs fast lookup
- Discreet UX vs enough visual clarity

## Drift Risks
- Becoming a gimmick instead of a daily-use assistant
- Feature sprawl before core subtitle/memory loop is excellent
- Interaction sprawl that adds command modes or hardware complexity before the touch-first V1 is excellent
- High-latency responses that break trust
- Storing low-value information instead of weighted relevant memory

## Why It Matters
The system should reduce social and cognitive friction for the wearer, especially in noisy environments, hearing-challenged situations, memory-challenged situations, and dense multi-person contexts. It should help the wearer stay present, informed, and confident without pretending understanding.

## Evolution Rule
The project is allowed to evolve beyond its original form if that evolution strengthens the core mission, improves real-world usefulness, or increases trust, clarity, and assistive value. Expansion is good when it deepens the core, not when it distracts from it.

## Reality Check Rule
The system should continuously surface real-world limitations early, including hardware, battery, thermal, latency, privacy, and usability constraints, so the project does not waste time optimizing impossible or low-value directions.

## Current Open Questions
- What is the best V1 split between glasses, phone, and cloud?
- How should face/name memory be stored and reinforced for fast lookup and trust?
- How should confidence be represented: numeric score, label, and short reason?
- How should subtitles and one-line prompts coexist without overloading the wearer?
- What is the best subtitle placement and visual hierarchy for fast reading with low distraction?
- Which V1 features produce the highest daily-use value with the lowest complexity?

## Reality Rules

### V1 Real World Limits
- **Glasses should remain lightweight and socially acceptable.**
- **Early versions should not depend on heavy on-glasses compute.**
- **Battery and thermals are major risks for always-on features.**
- **Subtitles must feel near-real-time or trust breaks.**
- **Face/name recall must expose uncertainty clearly.**
- **First versions should rely heavily on phone processing, with cloud optional where useful.**
- **The system should help the wearer understand, not fake understanding.**

### V1 Architecture Direction
- **Glasses: text display, lightweight sensors/input, minimal local logic.**
- **Phone: primary runtime for speech, context, memory lookup, and orchestration.**
- **Cloud: optional heavy lifting for deeper analysis, model upgrades, and non-critical background processing.**
- **Reduces on-glasses thermal and battery pressure.**
- **Makes iteration faster.**
- **Preserves a path to stronger local capability later.**
- **Keeps V1 focused on real utility instead of overbuilt hardware.**

### Interaction Constraints
- **V1 should not depend on voice activation or spoken user commands for controlling the glasses.**
- **User control should happen through frame touches only.**
- **Any suggested interaction pattern should respect this constraint unless the project explicitly changes direction later.**

## Feasibility Assessments

### Subtitle Placement: Feasible Now
- **Subtitle placement** should prioritize non-distracting, unobtrusive positions that do not interfere with the user's natural field of vision.
- **Feasibility**: Use a small, bottom-center corner display for subtitles to minimize visual intrusion while ensuring readability.

### Confidence Display: Feasible Later
- **Confidence display** is crucial for trust but may introduce complexity early on.
- **Feasibility**: Introduce a simple label or icon indicating the reliability of the subtitle (e.g., "high", "medium", "low") and consider adding short reasons later when resources allow.

### Memory/Cache Policy: Feasible Now
- **Memory policy** for face/name recall should be lightweight, relying on context and minimal data storage.
- **Feasibility**: Implement basic memory objects that are reinforced through repeated interactions. Use explicit remember-touch behavior to enhance trust.

### Phone/Cloud Boundary: Feasible Later
- **Phone/cloud boundary** will depend heavily on the success of V1 features before expanding into more complex cloud-based functionalities.
- **Feasibility**: Start with minimal cloud dependencies for essential services like model updates and consider additional cloud functionality as needed based on user feedback.

### Visual Hierarchy: Likely Waste of Time
- **Visual hierarchy** is a broad topic that may not add significant value early in V1.
- **Feasibility**: Focus initially on core functionalities (subtitles, memory recall) and refine visual design as the system matures. Consider simplified visual hierarchies to start with.
